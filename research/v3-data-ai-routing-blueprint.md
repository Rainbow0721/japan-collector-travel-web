# V3 真正可用的 AI 東京行程系統

## 現況判定

目前原型不是生成式 AI。`app.js` 只做以下工作：

1. 用字串比對找出美食、購物、神社、動漫、自然、夜景與親子等主題。
2. 對符合類別的地點加分，對使用者點名及收藏地點大幅加分。
3. 依區域分組，每天從一個區域挑選高分地點。
4. 用經緯度直線距離估算移動時間。
5. 用固定市區交通費或近郊交通費，加上門票及每日餐費估算總額。

它適合驗證介面，不足以對外宣稱 AI 私人地陪。

## 正式系統分工

### 1. AI 語意層

OpenAI Responses API 將自然語言轉成固定 JSON，不直接編造景點或票價：

```json
{
  "days": 5,
  "dates": ["2026-10-12"],
  "mustVisit": ["淺草寺"],
  "mustEat": ["壽司", "燒肉"],
  "interests": {"food": 0.9, "shopping": 0.8, "shrines": 0.5},
  "avoid": ["排隊超過30分鐘", "長距離步行"],
  "party": {"adults": 2, "elderly": 1, "children": 0},
  "budget": {"dailyJpy": 12000, "excludeShopping": true},
  "nearbyTrips": ["鎌倉"],
  "pace": "relaxed"
}
```

AI 還負責追問缺少但會改變結果的條件，例如住宿車站、抵達時間、旅遊日期、是否接受早起及近郊日。輸出必須用 Structured Outputs 驗證。

### 2. 候選地點檢索層

- 先從自有的 1,000 筆策展資料庫依區域、類別、營業日、同行者與預算篩選。
- 使用者搜尋長尾店家時，再即時呼叫 Places API／MapKit 搜尋，不把模型記憶當資料庫。
- 餐廳按餐別、料理、價位、排隊風險與營業時間處理，不能和公園使用同一評分公式。
- Google Place ID 可保存；其他 Google Places 內容依官方政策即時取得或在允許範圍內快取。

### 3. 行程最佳化層

不是讓語言模型自由排列，而是帶限制的最佳化問題：

- 必到景點與預約時段是硬限制。
- 營業時間、最後入場、旅行日期、出發飯店、回飯店時間是硬限制。
- 少轉乘、少步行、低花費、偏好符合、人氣與休息時間是可調權重。
- 近郊原則上一區一日；迪士尼、日光、箱根不得被當一般兩小時景點。
- 每段路線由地圖／交通 API 計算後，再執行排序；不是先排序再猜時間。
- 產生後再次檢查是否能在營業時間內到達，以及每天是否超出體力和預算。

### 4. 交通與費用層

每次排程都用真實出發日期與時間查詢：

- 大眾運輸：車站、路線、上下車時間、轉乘、步行、班次與可取得的票價。
- 計程車：道路路線時間、距離、預估跳表、迎車費、高速費與深夜加成；顯示區間而非假裝單一精確值。
- 包車／觀光巴士：使用供應商實際商品價格，按車輛、時數、人數與日期計算。
- 餐食：依早餐、午餐、晚餐與咖啡點心分項，不用「景點數 × 900」。
- 門票：使用官方票價及票種，區分成人、兒童、長者與快速通關。
- 交通票券：比較單程加總與地鐵券、JR Pass、箱根周遊券等，只有真的省錢才推薦。
- 個人購物永遠獨立，不計入基本旅費。

Google Routes 的大眾運輸路線可回傳站點、班次、步行段與部分路線票價，但只有所有區段都能確定時才會提供完整 transit fare。日本深度交通可評估 NAVITIME，其 API 支援繁中、時刻表選項、路線及費用資訊；時刻表屬額外合約。Apple Maps Server API 可提供地點搜尋、路線與 ETA，但仍需 Apple Developer 憑證。

## 1,000 筆不是單一搜尋

Google Text Search 每個查詢最多回傳 60 筆，因此要依「區域 × 類型 × 子類型」建立查詢矩陣，例如：

- 淺草 × 壽司、鰻魚、天婦羅、甜點、商店街、神社寺廟。
- 銀座 × 百貨、文具、甜點、壽司、精品、免稅店。
- 新宿 × 拉麵、燒肉、居酒屋、百貨、展望台、親子。
- 鎌倉 × 神社、寺廟、海景、咖啡、伴手禮、江之電沿線。

取得候選資料後還要去重、翻譯核對、歇業檢查、官網驗證及跨來源評分。`place-coverage-plan.json` 定義了 1,000 筆的區域與類別配額。

## 人氣排序

建議分數（0–100）由下列訊號組成：

- 地圖評分與評論量：25%。評論量須用對數正規化，避免 5.0 分但只有 3 則評論勝出。
- 去趣、Funliday、旅行社、Dcard／PTT 等跨來源共現：20%。
- 官方觀光單位或景點官網推薦：15%。
- 台灣／華語旅客相關性：15%。
- 近期營業及資料可信度：10%。
- 行程可組合性與交通便利：10%。
- 季節、排隊、預約和同行者適配：5%。

人氣只決定候選優先度，不能凌駕使用者明確偏好。

## 可參考產品

- Funliday：自有景點資料庫、AI 產生、真實旅行時間、拖拉後重算。
- Wanderlog：日程地圖、協作、預約整理、每日路線；全旅程自動最佳化仍有使用者反映限制。
- 去趣：地圖找景點、公開行程、推薦排行、共同記帳、行李清單與一鍵順路排序。
- Google Maps：即時地點與交通資料強，但不是完整的多日個人化行程產品。

本產品應採混合架構：AI 理解需求＋自有策展資料庫＋地圖／交通 API 驗證＋演算法最佳化＋使用者可拖拉修改。

## 實作順序

1. 建立後端與 PostgreSQL/PostGIS，不再把完整資料放在前端 JavaScript。
2. 選擇 Places 供應商及日本交通供應商，取得 API 金鑰並設定每日預算上限。
3. 依 coverage plan 匯入候選地點，人工驗證首批 200，再擴充至 1,000。
4. 串接 OpenAI Responses API，把需求輸出成固定結構。
5. 串接路線矩陣、營業時間及門票資料，完成單日最佳化。
6. 完成多日分區、近郊整日、長者／兒童／無障礙限制。
7. 建立 100 組測試需求，與人工專業行程比較成功率、折返、錯誤營業時間、費用誤差及使用者修改率。
